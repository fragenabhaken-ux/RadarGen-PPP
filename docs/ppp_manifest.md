## JSON contract and identity

The format is non-executable JSON (`radargen_ppp_manifest`, format version 1, validation version 1). It has a deterministic SHA256 identity over a canonical body and contains:

- resolved raw dataset and PPP HDF5 roots, split, dataset/version, preprocessing signature, HDF5 schema version and filtering policy;
- resolution/geometry/units, all normalization settings including camera frequency, reference sensor, camera/radar and conditioning order, illuminated-only selection, scene selection and any deliberately configured subset indices;
- the deterministic adapter order of scenes and consecutive pairs; relative sample paths, all expected metadata used by the existing item reader, file sizes and nanosecond mtimes, and validated positive target counts;
- per-scene expected frame/pair and directory inventory counts, and completion-record SHA256, size, and nanosecond mtime;
- total indexed sample count, zero empty-frame count, and the explicit metadata/header validation scope.

No training tensors or model/optimizer settings are serialized. Batch size, LR, GPU count, training duration, or update limit changes do not invalidate this dataset contract. Selection, geometry, normalization, roots, split, version, or preprocessing-signature changes do. Subset indices are recorded for diagnostic provenance; their manifest still indexes all pairs in the selected scenes, and training applies `Subset` afterward. Train and validation manifests are separate: a train artifact cannot be loaded with a validation contract.

Loading rejects unsupported versions, duplicate JSON keys, nonfinite numbers, unexpected/missing fields, invalid counts/types, path traversal, duplicate scenes, incorrect scene/frame order, malformed or missing expected metadata, inconsistent camera/radar order, checksum changes, and mismatched completion inventories. Filenames are reconstructed against scene/frame position rather than accepted as arbitrary paths. Completion bytes are checked against the recorded hash, and their sample size inventory must match the manifest. No executable deserialization is used.

The JSON checksum is an integrity/content identity, **not a signature proving that an untrusted author ran validation**. Use only manifests generated by the preparation command in trusted storage. Validation-version changes must accompany changes to adapter enumeration, expected metadata, header validation, or empty-frame rules; old manifests must then be rebuilt.

## Publication and immutable-data limits

A destination must be outside the immutable HDF5 root. Initial preparation refuses an existing destination before scanning. `--rebuild` explicitly revalidates and replaces it. The writer validates first, writes a sibling temporary JSON file, flushes and fsyncs it, then publishes atomically. Initial publication uses an exclusive hard link to avoid overwriting a concurrently created destination; rebuild uses atomic replacement. Failed validation, writing, fsync, or publication preserves the previous manifest, and temporary files are removed.

The dataset and raw adapter metadata must stay immutable during preparation and use. Fast startup does **not** detect every possible mutation: it does not rescan missing/extra/unaccessed HDF5 samples, re-enumerate the adapter, or detect changed raw metadata with the same configured root/version. Before every accessed item, the reader checks its recorded size/mtime and symlink status, then opens HDF5 read-only within a context manager, validates metadata/headers again, reads the consumed arrays, and runs the existing target and transformed-condition validation. No HDF5 handle is retained or inherited by workers. Missing or changed accessed samples fail; changed completion records fail at startup.

Size/mtime checks are **not cryptographic checks of sample contents**. A mutation preserving those values can escape the fingerprint check; per-item validation catches the existing semantic errors but is not a full content-integrity proof. Explicitly rebuild after any dataset/contract changes, including changed raw adapter metadata, and keep files immutable. No HDF5 locking settings are changed.

## Checkpoint compatibility

New manifest-backed training checkpoints add `manifest_identity` (format/validation versions and SHA256) to the existing strict training/data resume contract. Identity is captured before applying a diagnostic `Subset`. The JSON pathname is excluded from that checkpoint contract, so moving an identical manifest does not invalidate resume. Changing manifest contents/selection/fingerprints does invalidate it. Existing strict optimizer, batch, world-size, and other training resume checks remain; independence of the **manifest** from LR/GPU changes does not relax exact **checkpoint** resume compatibility.

Legacy checkpoints without a manifest identity are explicitly rejected for exact resume into manifest-backed training. There is no automatic migration or inference of dataset equivalence from length alone. Standalone checkpoint inspection/inference without a requested manifest resume contract remains supported. Preserve old diagnostic checkpoints; use their original checkout for exact legacy continuation or start a fresh manifest-backed training run. Tiny injected CPU tests retain the non-manifest path and are not a production scan fallback.
